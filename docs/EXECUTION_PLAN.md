# Web 发布工具执行文档

本文说明桌面应用如何执行一次打包、部署或源码发送。界面操作与安装命令见 [README](../README.md)。

## 项目与运行模式

发送端可以管理多个项目。点击「创建项目」时选择类型，后续操作都从具体项目卡发起。「部署项目」和「源码项目」共用本地构建配置，各自保存本地项目目录、Git 分支、ZIP 输出目录、接收端地址和 Token。同一本地目录可以建立两个独立项目。

| 项目类型 | 专用配置 | 操作与交付物 |
| --- | --- | --- |
| 部署项目（`kind: deploy`） | 构建命令、构建产物目录、Pages 项目与部署分支 | 「本地打包」生成本机构建产物 ZIP。「部署」重新构建、上传并提交一项 Pages 部署任务。 |
| 源码项目（`kind: source`） | 接收端公布的目录标识 `sourceTargetId` | 「本地打包」生成本机源码 ZIP。「打包并发送」生成并保存新的源码 ZIP，发送后取得远端版本路径。 |

应用默认以「仅发送端」模式启动。保存为「仅接收端」或「双端调试模式」后，下次启动应用会自动启动接收服务。同一接收地址和端口可同时支持部署与源码传输，接收端按请求路径分流。界面的「产物部署」和「源码接收」分别展示对应的配置与记录。

## 构建产物的打包与部署

1. 发送端按项目 ID 取得部署配置，核对当前 Git 分支，执行构建命令，并检查产物目录存在且非空。
2. 将产物目录内容写入 ZIP。「本地打包」到此结束并打开保存目录。默认输出目录是项目下的 `.web-publisher-artifacts/`。
3. 「部署」继续计算 ZIP 的 SHA-256，初始化上传，查询已接收的分片，并逐片上传缺失部分。上传标识由 Pages 项目、部署分支、文件哈希和大小生成。
4. 接收端合并并校验分片，创建部署任务。部署队列依次检查 ZIP 路径、解压文件，再调用 Wrangler 部署到配置的项目和分支。
5. 发送端根据部署 ID 轮询状态。部署记录显示 `queued`、`running`、`success` 或 `failed`，附带执行日志、错误信息或 Wrangler 返回的访问地址。任务状态与日志保存在当前接收端进程内。

## 源码快照、版本目录与重试

1. 接收端在「源码接收」中选择本机目录并命名，保存配置。发送端取得可用目录列表并选择一个目标。
2. 发送端核对所选 Git 分支，按项目根目录的 `.gitignore` 筛选当前工作目录。打包会保留符合规则的未提交改动、新文件和遍历到的 `.gitignore`，跳过 `.git`、发送缓存、项目内的 ZIP 输出子目录及本工具生成的源码 ZIP。筛选与压缩使用 Electron 自带的 Node.js 运行时。实现见[源码打包目录](../desktop/src/services/source-pack/)。
3. 发送端保存 ZIP 和待重试任务，按任务 ID 分片上传。接收端记录分片，校验整包后在目标文件系统的临时目录解压。解压成功后将目录重命名为最终版本并写入接收记录。
4. 新发送的版本路径为 `<接收目录>/<项目名称>/<YYYYMMDD-HHmmss>-<UUID>/`。在「源码接收」中可以打开该目录，重启接收端后仍可查看已完成记录。

| 发送端操作 | 使用的内容 | 接收端行为 |
| --- | --- | --- |
| 打包并发送（有待重试任务时为「重新打包并发送」） | 点击时的工作目录 | 创建新的任务和版本 |
| 继续原任务 | 原任务缓存的 ZIP、任务 ID 和目标目录 | 复用已接收的分片和版本路径。任务已完成时直接返回原结果。 |

源码任务的状态为 `uploading`、`extracting`、`success` 或 `failed`。传输中断后，保留发送端缓存和接收端工作目录，即可在原接收地址继续任务。源码接收流程只负责保存版本，Cloudflare 凭据用于构建产物部署。

## 接收端 HTTP 接口

部署和源码接口均使用 `Authorization: Bearer <token>`。健康检查使用 `GET /healthz`。

| 用途 | 方法与路径 | 结果 |
| --- | --- | --- |
| 初始化构建产物上传 | `POST /api/v1/uploads/init` | 返回上传 ID |
| 查询或上传产物分片 | `GET /api/v1/uploads/:id`、`PUT /api/v1/uploads/:id/chunks/:index` | 返回已收分片索引，或接收一个分片 |
| 提交产物部署 | `POST /api/v1/uploads/:id/complete` | 校验整包并返回部署 ID |
| 直接上传完整构建产物 | `POST /api/v1/deployments` | 请求体为 ZIP，`X-Metadata-Base64` 携带项目名和分支，可用 `X-Checksum-SHA256` 提交整包校验值 |
| 查询部署结果 | `GET /api/v1/deployments/:id` | 返回状态及当前任务已有的日志、地址或错误 |
| 获取源码目标目录 | `GET /api/v1/source/targets` | 返回接收端配置的目录 ID、名称和路径 |
| 初始化或恢复源码任务 | `POST /api/v1/source/tasks/:id/init` | 用同一任务 ID 和原始元数据恢复任务 |
| 查询或上传源码分片 | `GET /api/v1/source/tasks/:id`、`PUT /api/v1/source/tasks/:id/chunks/:index` | 查询任务状态，或接收一个分片 |
| 提交源码解压 | `POST /api/v1/source/tasks/:id/complete` | 开始校验和解压，成功后可查询最终版本路径 |

## 配置与文件位置

| 位置 | 内容 |
| --- | --- |
| 两端的 Electron 用户数据目录下的 `config.json` | 运行模式、项目配置、接收目录和凭据。导出的 JSON 也包含填写的 Token。 |
| 项目的「打包产物输出目录」，默认 `.web-publisher-artifacts/` | 保留本地打包、部署或发送时生成的 ZIP。源码发送另存一份独立的重试缓存。 |
| 发送端用户数据目录下的 `source-sends/` | 按项目保存的待重试源码包和任务信息 |
| 接收端工作目录，默认位于用户主目录下的 `web-publisher/` | `uploads/` 保存产物上传数据，`source-tasks/` 保存源码任务和接收记录。每个部署任务有独立的解压目录。 |
| 接收端命名的源码目录 | 按项目和版本保存解压后的源码文件 |

旧配置在加载或导入时迁移。普通旧项目归入部署项目，标记为源码专用的旧项目归入源码项目。旧部署项目若已配置源码接收目录，或本机留有待重试的源码任务，则拆成两条配置。源码项目沿用原 ID，使已缓存的传输可以继续。

## 验收

- **单项目操作**。配置两个部署项目，对其中一个执行「本地打包」，核对该项目生成的 ZIP 及接收端任务数。再点击该项目的「部署」，接收端应只增加该项目的一条部署记录。
- **源码独立版本**。发送一次源码，修改文件后再次发送，打开两个版本目录核对文件内容。在「源码接收」中应能看到两条记录。
- **中断续传**。中断分片传输，修改工作区并重启两端后选择「继续原任务」。核对接收内容来自第一次打包的快照，同一任务只产生一个版本。
- **自动化验证**。在 `desktop/` 下运行 `npm run lint` 和 `npm run test:source`。后者覆盖文件筛选、旧配置迁移、跨重启续传及新版本创建。
